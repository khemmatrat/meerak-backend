# AQOND Marketplace — Order Flow Specification (v1)

เอกสารนี้รวบรวม flow ฝั่งลูกค้า, order state machine, escrow logic, ระบบหลังบ้านร้านค้า และ edge case ที่ต้องออกแบบไว้ตั้งแต่แรก เพื่อให้ marketplace จบเป็น production-ready ก่อนขยายไปโปรดักส์อื่น

---

## 1. Customer-Side Flow (Full)

### 1.1 Discovery → Product Detail
1. ลูกค้าเปิดหน้าร้าน/ค้นหาสินค้า
2. คลิกสินค้า → เข้าหน้า Product Detail Page (PDP)
3. เลือกตัวเลือกสินค้า (ไซส์ / สี / variant) — ระบบต้องเช็ค stock ของแต่ละ variant แยกกัน ไม่ใช่ stock รวม
4. แสดงข้อมูล "คุ้มครองสินค้า" (buyer protection policy) — ต้องลิงก์ไปหน้า policy เต็ม ไม่ใช่แค่ badge
5. ลูกค้าเลือก **"เพิ่มลงตะกร้า"** หรือ **"ซื้อทันที"** (สองปุ่มแยกกัน — อย่ารวมเป็นปุ่มเดียว เพราะพฤติกรรมต่อไปต่างกัน)

### 1.2 Cart (ถ้าเลือกเพิ่มลงตะกร้า)
6. ลูกค้าดูตะกร้า ปรับจำนวน / ลบสินค้า
7. ระบบเช็ค stock ใหม่อีกครั้งตอนเข้าตะกร้า (stock อาจเปลี่ยนระหว่างที่ลูกค้าเลือกดูสินค้าอื่น)
8. กด "ดำเนินการสั่งซื้อ"

### 1.3 Checkout
9. เลือก/เพิ่มที่อยู่จัดส่ง (ต้องรองรับหลายที่อยู่ที่บันทึกไว้ ไม่ใช่กรอกใหม่ทุกครั้ง)
10. กรอก/เลือกโค้ดส่วนลด — ระบบต้อง validate เงื่อนไข (ขั้นต่ำ, สินค้าที่ร่วมรายการ, จำนวนครั้งที่ใช้ได้) แบบ real-time ไม่ใช่ validate ตอน submit เท่านั้น
11. เลือกวิธีชำระเงิน (QR PromptPay / บัตร / อื่นๆ)
12. **หน้าสรุปคำสั่งซื้อ (Order Review)** — จุดที่ flow เดิมขาดไป ต้องแสดง: รายการสินค้า, ค่าส่ง, ส่วนลด, ยอดรวมสุทธิ, ที่อยู่จัดส่ง, ให้ลูกค้ากด "ยืนยันคำสั่งซื้อ" อีกครั้ง
13. ระบบ **lock stock** ณ จุดนี้ (ไม่ใช่ตอน merchant confirm) พร้อมตั้ง timeout เช่น 15 นาที ถ้าจ่ายไม่ทันปล่อย stock คืน
14. สร้าง order ในสถานะ `PENDING_PAYMENT`

### 1.4 Payment
15. แสดงหน้า QR Code พร้อม countdown timer (อายุ QR)
16. ลูกค้าสแกนจ่ายผ่านแอปธนาคาร
17. ระบบรับ webhook จาก payment gateway → เปลี่ยนสถานะ order เป็น `PAID` (เงินเข้า escrow ของแพลตฟอร์ม ไม่ใช่เข้าร้านตรง)
18. แสดงหน้า "ชำระเงินสำเร็จ" → ปุ่ม "ดูคำสั่งซื้อ" ไปหน้ารายละเอียดออเดอร์ (ตรงกับภาพที่ 2 ที่ส่งมา)
19. กรณี QR หมดอายุก่อนจ่าย หรือลูกค้าปิดแอปกลางคัน → ต้องมี reconciliation job เช็คกับ payment gateway อีกครั้งก่อนสรุปว่า cancel จริง (กันเคส "จ่ายแล้วแต่ระบบไม่รู้")

### 1.5 Merchant Confirmation
20. ออเดอร์เข้าคิวร้านค้า สถานะ `AWAITING_MERCHANT_CONFIRM`
21. ร้านค้ากด "รับออเดอร์" หรือ "ปฏิเสธ" (ของหมด/ผิดพลาด) — ถ้าปฏิเสธ ระบบคืนเงินอัตโนมัติทันที ไม่ต้องรอลูกค้าขอ

### 1.6 Fulfillment
22. ร้านค้าแพ็คสินค้า อัปเดตสถานะ `PACKED`
23. ร้านค้ากรอกเลข tracking → สถานะ `SHIPPED`
24. ลูกค้าติดตามพัสดุผ่านลิงก์ tracking (ตรงกับปุ่ม "ติดตามพัสดุ" ในภาพที่ 2)
25. ระบบ courier อัปเดตสถานะจนถึง `DELIVERED`

### 1.7 Post-Delivery (จุดสำคัญของ escrow)
26. เมื่อสถานะเป็น `DELIVERED` ระบบเปิด **auto-confirm window** (แนะนำ 3–7 วัน)
27. ในช่วงนี้ลูกค้าเลือกได้ 2 ทาง:
    - กด "ยืนยันรับสินค้า" ทันที → ปล่อยเงินให้ร้าน + เปิดให้ให้คะแนน (ตรงกับ tab "ให้คะแนน" ในภาพที่ 1)
    - ไม่กดอะไรเลยจนครบกำหนด → ระบบ auto-confirm ให้ (ปล่อยเงินอัตโนมัติ)
    - กด "ขอคืนเงิน" ก่อนครบกำหนด → เข้า return flow (ดูหัวข้อ 3)

## 2. Order State Machine

| สถานะ | ความหมาย | ทริกเกอร์เข้า | ทริกเกอร์ออก |
|---|---|---|---|
| `PENDING_PAYMENT` | รอชำระเงิน, stock ถูก lock ชั่วคราว | ลูกค้ายืนยันคำสั่งซื้อ | จ่ายสำเร็จ → `PAID` / timeout → `CANCELLED` |
| `CANCELLED` | ยกเลิก, stock ถูกปล่อยคืน | timeout ไม่จ่าย | (จบ) |
| `PAID` | จ่ายแล้ว เงินอยู่ใน escrow แพลตฟอร์ม | webhook ยืนยันจาก payment gateway | ร้านรับ → `MERCHANT_ACCEPTED` / ร้านปฏิเสธ → `REFUNDED` |
| `REFUNDED` | คืนเงินให้ลูกค้าเต็มจำนวน | merchant ปฏิเสธ / return อนุมัติ | (จบ) |
| `MERCHANT_ACCEPTED` | ร้านรับออเดอร์แล้ว | ร้านกดรับ | เริ่มแพ็ค → `PACKED` |
| `PACKED` | แพ็คสินค้าเสร็จ รอส่ง | ร้านอัปเดต | กรอก tracking → `SHIPPED` |
| `SHIPPED` | ส่งสินค้าแล้ว มีเลข tracking | ร้านกรอกเลขพัสดุ | courier confirm → `DELIVERED` |
| `DELIVERED` | ลูกค้าได้รับสินค้าแล้ว เปิด auto-confirm window | courier system | ลูกค้ายืนยัน/auto-confirm → `COMPLETED` / ลูกค้าขอคืน → `RETURN_REQUESTED` |
| `RETURN_REQUESTED` | ลูกค้าแจ้งขอคืนสินค้า/เงิน พร้อมหลักฐาน | ลูกค้า submit ฟอร์ม | เข้า review → `UNDER_REVIEW` |
| `UNDER_REVIEW` | แอดมิน/ร้านกำลังตรวจสอบหลักฐาน | เข้าคิว review | อนุมัติ → `REFUNDED` / ไม่อนุมัติ → `COMPLETED` |
| `COMPLETED` | เงินถูกปล่อยให้ร้านค้าแล้ว | ยืนยันรับของ/auto-confirm/return ไม่ผ่าน | (จบ, เปิดให้ rating) |

**กฎสำคัญ**: เงินจะเข้าบัญชีร้านค้า (พร้อมถอนได้) เฉพาะเมื่อ order สถานะเป็น `COMPLETED` เท่านั้น ทุกสถานะก่อนหน้าเงินอยู่ใน escrow ของแพลตฟอร์ม — ตรงกับที่คุณระบุว่า "ไม่ปล่อยให้เจ้าของร้านได้เงินกรณีเกินข้อพิพาท"

## 3. Return / Refund / Dispute Flow (เติมจากภาพที่ 3)

ฟอร์มในภาพที่ 3 ขาดขั้นตอนการตรวจสอบ ต้องเติมดังนี้:

1. ลูกค้าเลือกเหตุผล + วิธีส่งคืน (ตรงกับภาพ) **+ บังคับแนบรูปหลักฐานอย่างน้อย 1 รูป** (ปัจจุบันมีแค่ text field)
2. ระบบสร้าง case เข้าคิว `UNDER_REVIEW` พร้อม SLA (เช่น ต้องตอบภายใน 48 ชม.)
3. ผู้ตรวจสอบ (ร้านค้าก่อน หรือ admin ถ้าร้านค้ากับลูกค้าเห็นไม่ตรงกัน) ดูหลักฐาน:
   - **อนุมัติ** → กำหนดวิธีคืนสินค้า (ถ้าต้องส่งคืนจริง) → เมื่อร้านยืนยันได้รับของคืน → คืนเงินลูกค้าเต็มจำนวนหรือบางส่วนตามนโยบาย
   - **ไม่อนุมัติ** → แจ้งเหตุผลลูกค้า → ปล่อยเงินให้ร้าน (`COMPLETED`)
4. ถ้าร้านค้ากับลูกค้าเห็นไม่ตรงกัน (ร้านปฏิเสธ แต่ลูกค้าไม่ยอมรับ) → ต้อง escalate เป็น `DISPUTE` ให้ admin ของแพลตฟอร์มตัดสินขั้นสุดท้าย พร้อม timeline ที่ทั้งสองฝ่ายเห็นตรงกันว่าจบเมื่อไหร่
5. ค่าส่งคืน: ต้องกำหนดนโยบายชัดว่าใครจ่าย (ลูกค้าจ่ายถ้าสินค้าไม่มีปัญหาจากร้าน / ร้านจ่ายถ้าสินค้าชำรุด/ผิดปก)

## 4. Escrow / เงินหมุนเวียน

```
ลูกค้าจ่ายเงิน → Payment Gateway → Escrow Wallet (แพลตฟอร์มถือ)
                                        │
                        [รอจนสถานะ order = COMPLETED]
                                        │
                                        ▼
                    หัก commission แพลตฟอร์ม → เข้า Merchant Wallet (pending)
                                        │
                        [รอบตัด settlement เช่น T+3 วันทำการ]
                                        │
                                        ▼
                              โอนเข้าบัญชีธนาคารร้านค้า
```

จุดที่ต้องออกแบบเพิ่ม:
- **Merchant Wallet ต้องแยก 2 balance**: `pending balance` (เงินจาก order ที่ยังไม่ COMPLETED) กับ `available balance` (ถอนได้จริง) — ร้านค้าต้องเห็นทั้งคู่ในหน้า dashboard เพื่อไม่สับสน
- ทุก transaction (hold, release, refund, commission) ต้องมี ledger log แบบ append-only เพื่อ audit ย้อนหลังได้ — อย่าอัปเดต balance โดยตรงโดยไม่มี log
- Reconciliation job รายวัน เทียบยอดใน escrow wallet กับยอดจริงที่ payment gateway ยืนยัน

## 5. Merchant Backend (หลังบ้านร้านค้า)

ต้องมีอย่างน้อยโมดูลเหล่านี้:

1. **Order Queue** — แยกแท็บตามสถานะ: ใหม่ (รอรับ) / กำลังแพ็ค / จัดส่งแล้ว / เสร็จสิ้น / ขอคืนสินค้า/ข้อพิพาท — ตรงกับ UI ฝั่งลูกค้าในภาพที่ 1 ที่มี tab คล้ายกันอยู่แล้ว
2. **สินค้า/สต็อก** — จัดการ variant (ไซส์/สี) แยก SKU, จำนวนคงเหลือ, ราคา, รูปสินค้า
3. **Escrow / Wallet Dashboard** — pending balance, available balance, ประวัติ transaction, ปุ่มขอถอนเงิน
4. **การจัดส่ง** — กรอก tracking number, เลือก courier, พิมพ์ label (ถ้ามี)
5. **Return/Dispute Center** — ดูเคสที่ลูกค้าขอคืน, อนุมัติ/ปฏิเสธ พร้อมแนบหลักฐานโต้แย้ง
6. **โปรโมชัน/โค้ดส่วนลด** — สร้าง/จัดการโค้ดของร้านตัวเอง
7. **รายงานยอดขาย** — แยกตามช่วงเวลา, สถานะ commission ที่โดนหัก
8. **แชทกับลูกค้า** — สำคัญมากสำหรับลดข้อพิพาทก่อนขึ้นเป็น dispute จริง

## 6. Edge Cases ที่ต้องตัดสินใจตั้งแต่ตอนนี้ (ก่อนเริ่มเขียนโค้ด)

- สต็อกเหลือ 1 ชิ้น มีคนกด "ซื้อทันที" พร้อมกัน 2 คน → ใครได้สิทธิ์? (แนะนำ: lock ด้วย DB transaction ตอนเข้า `PENDING_PAYMENT` คนแรกที่ lock ได้คือคนได้สิทธิ์ คนที่สองแจ้ง "สินค้าหมด" ทันที)
- ลูกค้าจ่ายเงินสำเร็จแต่ webhook มาช้า/หาย → ต้องมี job poll สถานะกับ payment gateway ทุก N นาทีสำหรับ order ที่ค้างใน `PENDING_PAYMENT` เกินเวลาที่กำหนด
- ร้านค้าไม่ตอบสนอง order ค้างในคิวนานเกินไป → ต้องมี SLA auto-cancel + คืนเงินลูกค้า ถ้าร้านไม่รับภายในเวลาที่กำหนด
- Courier ส่งของไม่สำเร็จ (ที่อยู่ผิด, ลูกค้าไม่รับ) → ต้องมีสถานะ `DELIVERY_FAILED` แยกจาก flow ปกติ พร้อมกำหนดว่าใครรับผิดชอบค่าส่งกลับ
- ลูกค้ายกเลิกออเดอร์หลังร้านรับแล้วแต่ยังไม่แพ็ค → ต้องมี cancellation policy แยกจาก return policy (ไม่ใช่กรณีเดียวกัน)
- ร้านค้าปลอมเลข tracking เพื่อเร่งปล่อยเงิน → ควร integrate courier API เพื่อ verify สถานะจริง ไม่เชื่อแค่เลขที่ร้านกรอกเอง

## สรุปลำดับที่ควรทำใน MVP

**Must have (launch ไม่ได้ถ้าขาด):** state machine หัวข้อ 2 ทั้งหมด, escrow logic พื้นฐาน, order review ก่อนจ่ายเงิน, merchant accept/reject, auto-confirm timer

**Should have (ทำตามหลัง 2-4 สัปดาห์):** return/dispute UI เต็มรูปแบบ, merchant wallet dashboard แบบละเอียด, promotion engine

**Can wait:** chat กับลูกค้าในแอป, รายงานเชิงลึก, multi-courier integration
